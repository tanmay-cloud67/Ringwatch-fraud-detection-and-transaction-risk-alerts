Statuses reflect the current implementation and evidence collected so far. A separate A–P report will distinguish passed checks from items that remain unverified or blocked.

## 1. Product purpose and architecture — COMPLETE
- RingWatch is an investigator-led fraud and transaction-risk demo for a finance hackathon. It shows connections between accounts, not just alerts; scores transactions, groups suspicious activity into cases, draws how money moves between accounts, and explains alerts in plain English. One fraud ring should be one connected alert rather than many disconnected alerts. It supports investigators and never blocks transactions or makes final decisions.
- Keep Python FastAPI, pandas, scikit-learn IsolationForest, NetworkX, and a single-page vanilla HTML/CSS/JavaScript frontend. Use the supplied local Chart.js, vis-network, and Tailwind assets. Do not add a database, paid/external APIs, CDN dependencies, or runtime internet requirements. Keep all state in process memory and disclose that it is lost on restart/redeploy. Centralize thresholds in `config.py`; use fixed random seed 42 for the sample, Isolation Forest, and stochastic graph operations.
- Evidence: source/runtime audit, local asset inventory, project configuration (`server=true`, `database=false`), API tests, and browser Preview.

## 2. CSV ingestion, sample data, and data-quality reconciliation — COMPLETE
- Required headers are exactly `txn_id,timestamp,from_account,to_account,amount,channel,city,device_id`; optional `is_fraud` is 0/1 and is used only for evaluation, never as a rule, model input, feature, case score, or sort key. Parse timestamps consistently as UTC and sort accepted records by time.
- File-level rejection returns HTTP 400, a clear human-readable message, and leaves the previous dataset untouched for missing required columns (naming the missing columns), empty or unparseable files, non-CSV uploads, files over 20 MB, and files over 100,000 source rows.
- Row-level rejection drops and records a reason for any missing/blank required value, unparseable timestamp, amount that is not positive, malformed-width record, or `from_account == to_account`. Exact duplicate rows compare all eight required columns, keep the first, and increment `duplicates removed`; a later row with the same `txn_id` but different required-column content is rejected as `conflicting_txn_id`. The UI states this duplicate/reused-ID policy and rejected rows can be downloaded with their reasons.
- Data Quality shows raw rows, rejected rows and reason breakdown, exact duplicates removed, processed rows, and a green equality or red warning for `raw = rejected + duplicates + processed`.
- Seed-42 sample generation creates about 3,000 normal transactions over 200 accounts plus 30 planted `is_fraud=1` transactions: five ₹47,000–₹49,500 transfers from one sender within two hours; a near-equal A→B→C→D→A cycle within 24 hours; 12 distinct senders funding one recipient that forwards at least 90% within one hour; and eight around-3AM transfers in under ten minutes from a new city/device. Show the injected count, provide “Load sample data” and “Download sample_transactions.csv”, and keep the generated output identical on every run.
- Evidence: 17-test suite, deterministic checked-in CSV comparison (3,030 rows, 200 accounts, 30 injected labels), upload preservation/error tests, malformed-row and duplicate-policy tests, browser Dashboard, and live health/API checks.

## 4. Explainable detection rules — COMPLETE
- All point values and thresholds are configurable in `config.py` and editable in Settings. Defaults are structuring 45, velocity 30, odd-hours 25, new-device/city 20, circular-flow 50, and fan-in/pass-through 50. Each matched transaction receives rule points and a plain-English reason containing observed evidence and the threshold used.
- Structuring: at least three transfers by one sender within two hours, each between 90% and 99% of the illustrative ₹50,000 threshold. Velocity: more than six transfers by one sender in ten minutes. Odd hours: 1AM–5AM UTC and at least three times the average of the sender’s other transactions. New device/city: first-seen sending-account context only after at least five earlier transactions and above the configured amount threshold (default ₹20,000). Circular flow: timestamp-valid directed cycles of 3–5 accounts within 48 hours; ignore self-loops and two-cycles. Fan-in/pass-through: at least eight distinct senders and at least 80% of received value forwarded within one hour.
- Evidence: crafted positive tests for all six rules, crafted near-miss cases for each, configured points/model-contract assertions, and sample-data rule evidence.

## 5. Machine-learning score, explanations, and label isolation — COMPLETE
- Run a 200-tree Isolation Forest with `random_state=42` using exactly these six transaction features: amount compared with account average, transaction count in the last hour, transaction count in the last 24 hours, hour of day, distinct counterparties, and seconds since the account’s previous transaction. Never use `is_fraud`, transaction ID, or other labels in rules, features, training inputs, risk calculation, or sort keys.
- Scale the model anomaly signal to 0–100, where higher means more unusual relative to this dataset; state that it is not a fraud probability. Combined risk is exactly `final_risk = min(100, rule_points + 0.4 * ml_score)`. Flag transactions at the configurable default threshold 40; configurable risk bands are Low <40, Medium 40–69, and High ≥70. Show top plain-English reasons wherever a score is displayed.
- Show the formula in Pipeline with a live worked example from a real transaction; show at least three worked examples, including one capped at 100. Case detail gives top-transaction rule points, model score, weighted `0.4 * ml_score` contribution, and capped final risk.
- Evidence: model-contract and formula/cap tests, label-flip and label-removal invariance checks for scores/rules/cases, API label isolation, and populated Pipeline/Network case detail.
